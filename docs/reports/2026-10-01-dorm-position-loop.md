# 宿舍地面位置环对照（2026-10-01）

> 本文按 10 月 1 日实验时点记录；其中“尚未刷写”“固件版本未知”不代表 10 月 2 日现状。后续已确认出厂 V1.1.3 并完成多组固件静态测频，见 [2026-10-02 固件与车端探测记录](2026-10-02-firmware-probe.md)。

第二趟是目前较好的**无碰撞候选参数**，不是已完成实车定位验收。用户补充：第三趟的**中点运动在现场看来最稳、最好**，但返程右弧或后退段过冲后停顿一会儿才平滑回正，并发生碰撞。第三趟虽然程序按轮式 odom 判稳，但不能用 odom 的终点误差取代现场结果；odom 给出的中点过冲比第二趟大，也不能覆盖用户对实际车身运动的观察。三趟场地起始摆位靠人工复位，物理真值没有外部测量。

第一趟返程末段，在 `t=1224.801`，按日志重算的位置控制器原始车体前向命令已经是 `+0.066 m/s`，实际发布仍是 `−0.273 m/s`；越过目标前向坐标时原始命令 `+0.081`，实际发布 `−0.213 m/s`。这是末级 `0.6 m/s²` 指令减速限幅把旧方向保留约 0.45 秒的直接证据。把**指令**减速上限单独改到 3.0 后，中点和返程过冲明显下降；此值不表示车体物理减速度已达到 3.0 m/s²。三趟试验时的默认值为 `kp=1.0`，第三趟的 `kp=1.5` 仅通过命令行传入；试验结束后按用户要求把默认值改为 `1.4`，尚未实车试跑。

第二趟返程到 HOLDING 时位置误差约 2.5 cm、平移速度约 0.10 m/s；约 0.9 秒后位置进入 2.5 cm 容差。之后轮式 odom 低速读数在 0–0.026 m/s 间波动，几次超过 0.025 m/s 的停稳速度门槛，重置 0.3 秒双时钟停稳计时。没有证据支持靠缩短计时来解决物理回正。

新 CSV 为每次 `/odom_raw` 回调单独记录源时间戳与接收单调时钟。三趟源时间戳推进约 11.1 Hz；在车上独立执行 `ros2 topic hz /odom_raw` 也约 11 Hz，故不能再把这一频率差完全归因于 Python 控制回调。单项 `Publisher_odom` **样例**将 timer 设为 50 ms，但现场节点是 `YB_Node`，样例节点名为 `YB_Example_Node`。不能从样例推断实车的轮速 PID 参数；尚未确认烧录版本。

同日车端静止时分别运行约 8 秒 `ros2 topic hz`：`/odom_raw` 约 11.2 Hz、`/imu/data_raw` 约 25.0 Hz、`/scan0` 和 `/scan1` 各约 7.1 Hz。三项与厂商 `Publisher_imu` 和 `Publisher_lidar` 样例头文件共同定义的 `ODOM=90 ms`、`IMU=40 ms`、`LIDAR=140 ms` 定时器宏逐项吻合。这强烈提示出厂集成固件沿用该组发布周期，但这两个样例只注册自身功能的 timer，不能作为实车固件的直接证据。现场 `ros2 node info /YB_Node` 证实三个传感器话题由同一个 micro-ROS 底盘节点发布；11 Hz 不是整个节点共用的速率。车端 `~/config_robot.py` 可读固件版本和修改电机/IMU PID、里程计比例，但未找到里程计发布频率选项。读取版本需要暂时独占与 Agent 共用的 `/dev/myserial`，本次未中断 Agent。

厂商公开 Google Drive 的 `6.Firmware_DriverFile/Control board factory firmware` 目录可见 `microROS_STM32-FW_V1.1.3.hex`（971 KB，显示修改时间 2025-08-28）；这是已编译出厂镜像，不是可编辑的集成 C 源码，也不能仅凭文件名证明实车已烧录同一版本。当前车上 `/cmd_vel` 发布者为 0，Agent 仍在线；未查询固件版本、未刷写。

用户另从官网取得 `~/Downloads/microROS_STM32-FW_V1.1.2.hex`，SHA-256 为 `1e27ea266e772d075b633549091f64befa5f5ae4f446224878ea50f8e788d2a7`。Intel HEX 校验和全部通过，映射约 353 KB；静态字符串包含 `YB_Node`、`odom_raw`、`imu/data_raw`、`scan0`、`scan1`、`battery`、`cmd_vel` 和机械臂相关话题。这证明该 HEX 是集成功能的编译固件。当前仓库 `Board_Samples/Microros_Samples` 只有九个独立教学 CubeIDE 工程，未找到与 `YB_Node` 对应的集成源码；这仅限定于当前仓库，不能推断厂家其他资料包也没有源码。

对 V1.1.2 HEX 的 Thumb 反汇编进一步确认：`odom_raw` publisher 在 `0x0800B51A` 初始化后，`0x0800B552` 的 timer-init 调用读取 `0x0800B790` 处的 64 位常量 `90,000,000 ns`，即 **90 ms / 11.11 Hz**。同一初始化代码的 IMU timer 读取 `40,000,000 ns`，`scan0`、`scan1` 读取 `140,000,000 ns`。这与现场实测约 11.2/25/7.1 Hz 匹配，足以认定 V1.1.2 固件的 odom **初始发布周期**为 90 ms；不能仅由匹配证明现场固件版本相同。`config_robot.py` 的公开命令表列出电机/航向 PID、域 ID、命名空间和速度缩放等，没有 odom 发布周期项。反汇编目前未找到该 90 ms 常量的运行时写入或配置字段，但这还不能证明固件绝无隐藏命令。未向控制板发送未知命令，也未刷写 HEX。

底盘控制板重新上电后，已通过车端 `m3.sh up` 重启 Agent 并恢复 `/YB_Node`、`/odom_raw`、IMU 和双雷达 topic；此次未发送运动指令。现场烧录版本仍待只读查询，查询配置串口需先与运行中的 Agent 协调独占。单项 `Publisher_odom` 样例的 50 ms 定时宏已在本地暂改成 20 ms，但尚未编译或刷写；该工程缺少厂商集成固件的多项功能，不能作为直接替换方案。

已另用 `software/tools/patch_factory_odom_hex.py` 从 V1.1.2 原件离线生成 `field_data/microROS_STM32-FW_V1.1.2-odom20ms.hex`（SHA-256 `0158f1224fd51e12a3ba05cca04bbbbf7c1a2f231dbf6c7748d1a198de994ace`）。源文件 SHA、目标 90 ms 常量唯一性、22,079 条 HEX 记录校验和和重解码后全映像差异均已验证：仅 `0x0800B790` 所在的一条记录发生变化，四个数据字节不同，其他地址字节一致。此产物是**未烧录候选**；必须先确认车上实际固件与 V1.1.2 的硬件/版本兼容，保留可回退的原镜像，并在写入后读回校验及实测 odom/IMU/双雷达帧率。仅检查 HEX 格式无法证明在板上可正常运行或达到 50 Hz。

2026-10-02 又逐字节核对用户从网页版 GPT 下载的两个 HEX：`~/Downloads/microROS_STM32-FW_V1.1.2_odom_50Hz.hex` 的 353,064 个映射字节与上述本地 20 ms 候选**完全一致**；文件 SHA 不同仅因为网页版文件把所有 CRLF 换行为 LF，换行标准化后两份文本也完全一致。`~/Downloads/microROS_STM32-FW_V1.1.2_odom_20Hz.hex` 在同一地址写入 50,000,000 ns，与原厂 90 ms 映像也仅有该定时值四字节差异。三个版本的全部 22,079 条 HEX 记录校验和均通过；以上仍是离线验证，不是刷写验收。

故障停机路径已删除同方向非零“制动斜坡”，立即连续发布零速，并在零速窗口继续记录 odom。随仓库的固件样例对零命令执行 `STOP_BRAKE`；实车制动效果仍须由观测检验。第一趟零速窗口里 odom 从约 `(-0.0844,-0.0295)` 收敛至 `(-0.0856,-0.0288) m`，这只量到轮式里程计的短时变化，不是外部真实停车距离。

第二、三趟在相同的 `command_decel=3.0` 下，第三趟弧段里程计走廊最大偏差约 5.4 cm（第二趟约 2.9 cm），最终指令也更频繁触及 0.5 m/s 上限。控制输出约 50 Hz，所用 odom 样本年龄中位约 58 ms、95 分位约 98 ms；它会在多个控制周期内重复。平滑闭环记录不能可靠分离底盘电机响应延迟。用户随后要求把共享位置环和试跑默认 `kp` 固定为 1.4；这是明确的参数决定，**尚无 1.4 的实车验收**。

三趟移动段离线核对：控制记录分别为 286/286/284 条，对应新里程计时间戳仅 66/67/65 个，通常每帧重复 4–5 个 50 Hz 控制周期；绝大多数重复组的命令在同一旧里程计下继续变化。返程 profile 结束时，第二、三趟的 odom 平移速度仍约 0.10/0.09 m/s，随后靠 HOLDING 位置保持才收敛；第一趟则因走廊越界中止。这支持把“只在新 odom 到达时重算反馈、50 Hz 继续监控并重发最近命令”列为单变量对照实验，**不证明它会消除过冲**。简单把全程序循环降为 11 Hz 不会增加传感器信息，也会降低命令与安全检查频率。

后续若继续提高速度，先获取独立物理位姿真值（雷达/固定测量）并查明实际烧录固件与约 11 Hz odom 发布节奏；不要仅凭程序 `settled` 放宽走廊阈值或改动轮速 PID。碰撞发生后，本轮没有再发运动命令，试跑进程已退出，`/cmd_vel` 发布者数为 0。
