## 一、这台车的启动链路（Orin 版）—— 已实测确认

**开机自启的 4 个项**（`~/.config/autostart/`，2026-09-22 实读）：

| 自启文件 | Exec 内容 | 作用 | 对应窗口 |
|---|---|---|---|
| **`agent_autostart .desktop`**<br>⚠️ 文件名里**含一个空格** | `/home/jetson/start_agent.sh`<br>`Terminal=true` | **通讯代理** | `client key` 那个 |
| `check_sensor.desktop` | `gnome-terminal -- bash -c 'source /opt/ros/humble/setup.bash && export ROS_DOMAIN_ID=30 && sleep 5 && python3 /home/jetson/check_sensor.py; read -p ...'` | 检查雷达/时钟 | **`wait for scan0` 那个** |
| `joy_control.desktop` | `/home/jetson/joy_control/joy.sh` | 手柄控制 | 第三个 |
| `set.desktop` | `sh /home/jetson/set.sh`（"Start ROS Agent after 30 seconds"） | **也是起 ROS Agent**，延迟 30 s | 可能不显窗口 |

> ⚠️ `agent_autostart .desktop` 和 `set.desktop` **都在起 ROS Agent** —— 两者可能一个成功一个失败（历史遗留），
> 手动启动时**只跑一个**，别两个都跑（见第四节：代理不能重复启）。

**🔑 这台车的 `ROS_DOMAIN_ID = 30`** —— 从 `check_sensor.desktop` 的 Exec 里读到：
`export ROS_DOMAIN_ID=30`。与第五节「domain 必须一致」对应。

**Orin 与 nano/树莓派的根本区别**（`2.登陆小车并且查看代码.pdf` 原文：

> "**Orin 主板的代码是放在 `/home/jetson` 目录下的**，所以只要我们能够连接小车，就能够看到代码；
> 树莓派 5 和 jetson-nano 主板的代码，是放在启动的 docker 容器中"）

→ **Orin 不用进 docker**（实测 `docker ps -a` 只有一个 13 个月前退出的无关容器）。
→ 只有 nano/树莓派才需要 `sh Docker_M3Pro.sh` 进容器。

**自启动靠「桌面登录」触发** —— `~/.config/autostart/` 里的项由 GNOME 在**用户登录桌面后**执行
（每个文件都有 `X-GNOME-Autostart-enabled=true`）。

> ⚠️ **所以：只 SSH 进去、没在车的桌面上登录 → 这 4 项都不会跑 → 代理和手柄都没起
> → `ros2 topic list` 全空。这不是故障，是机制。**

**手动复现代理启动（不走桌面登录）**：

```bash
ssh car "export DISPLAY=:0; nohup bash ~/start_agent.sh > /tmp/agent.log 2>&1 &"
```

（`export DISPLAY=:0` 是必需的 —— 没它脚本报 `Cannot open display`；2026-09-22 实测有效，
代理起来后 `/arm6_joints` 出现。）

## 二、机械臂"没扭矩"是正常的（官方明确）

`常见问题及注意事项.txt` 第 2 条原文：

> "机械臂上电处于没有扭矩状态，**这种情况为正常**，使用
> `ros2 topic pub /arm6_joints arm_msgs/msg/ArmJoints {"joint1: 90, joint2: 90, joint3: 90,
> joint4: 90, joint5: 90, joint6: 90, time: 1500"} --once`
> 给机械臂发送角度后机械臂会**回复扭矩状态**。"

→ **这就是"让机械臂立起来"的官方方法：发一次角度指令。**
→ 前提：`/arm6_joints` 话题存在（即代理已起）。

## 四、⚠️ 通讯代理不能重复启

`常见问题及注意事项.txt` 第 4 条原文：

> "开启通讯代理卡住失败：使用 `docker ps` 指令查看有无重复开启的代理程序，
> 看到名称有包含 `ros-agent` 则说明代理正在运行，**无需反复重启多个代理**。"

→ **两个代理会抢同一个串口**，只会越搞越坏。判断代理在不在，用话题或进程，不要盲目重启它。

## 五、⚠️ ROS_DOMAIN_ID 必须两边一致

`7.修改小车控制板的固件参数.pdf` 原文：

> "`set_ros_domain_id` 表示设置小车 ROS DOMAIN ID，范围为 0~100……
> **注意要和系统终端 `.bashrc` 中的 `ROS_DOMAIN_ID` 值保持一致才可以通讯。**"

→ 如果改过 domain，底板和 `.bashrc` 必须同值，否则**话题看不到**。

## 六、唯一需要关代理的场景

`7.修改小车控制板的固件参数.pdf` 反复强调：

> "**运行修改配置脚本前，需要先关闭 microros 代理。**"

→ 这就是"标定中位值 / 改固件参数前要先关代理"的原因：脚本要**独占串口** `/dev/myserial`。
→ 除此之外**不要关代理** —— 关了等于把上位机到底板的桥拆了，`/cmd_vel` `/arm6_joints`
`/odom_raw` `/scan0` `/scan1` 全部消失。

## 八、日常使用约定（2026-09-22 用户定）

- **传文件**：Mac **普通终端** `scp 文件 car:~/`（一次性操作）
- **远程操控车**：Mac 开一个终端 **`ssh car` 进去（交互式）**，在里面跑命令

## 九、⚠️ 车端时钟每次重启都会漂（必须校时）

**现象**：`TF_OLD_DATA ignoring data from the past for frame base_footprint` 刷屏，
EKF 全部丢数据 → `/odom` 出不来 → 标定转不停。

**根因**：车没有可靠 RTC，重启后系统时间漂移，时间戳"来自过去"的数据全被丢。
**2026-09-22 实测：手动校时后警告立刻消失，EKF 正常。**

**每次重启小车后的固定动作**（Mac 终端）：

```bash
ssh car "echo yahboom | sudo -S date -s \"$(date '+%Y-%m-%d %H:%M:%S')\""
```

**校时后必须重启那些已经跑起来的 launch**（EKF/滤波器内部攒着坏时间戳）。

## 十、RViz 可视化（2026-09-22 深夜踩坑全记录，已闭环 ✅）

**现在的成品**：应用菜单「**RViz 雷达**」→ 打开即配好
（Fixed Frame=`base_link`，预置 `/scan0` `/scan1` `/scan_multi` 三个 LaserScan + TF，
QoS 全部 Best Effort——传感器数据标配，Reliable 会匹配不上）。

**构成**：
- 配置文件：车上 `~/radar.rviz`（源：`software/tools/radar.rviz`）
- 启动器：车上 `~/.local/share/applications/rviz.desktop`（源：`software/tools/rviz-desktop.desktop`）

**启动器 Exec 必须做三件事，缺一不可**：

```bash
source /opt/ros/humble/setup.bash
source ~/yahboomcar_ws/install/setup.bash
source ~/M3Pro_ws/install/setup.bash      # ← 缺它报 Package [M3Pro] does not exist（车体 STL 加载失败）
export ROS_DOMAIN_ID=30                    # ← 缺它看不到任何话题
rviz2 -d ~/radar.rviz
```

**当晚踩的坑（下次直接查表）**：

| 坑 | 教训 |
|---|---|
| 报错来自**旧窗口**，时间戳是 1 小时前的 | 判断报错先看**时间戳**，旧终端别关会一直留着误导 |
| 改了 `.desktop` 但启动还是旧行为 | GNOME 会缓存条目 → `update-desktop-database`，不行就**注销重登桌面** |
| 同名图标可能在多处（Desktop + 应用菜单） | 改一处≠全改；用 `grep -rl 旧标识` 找出**所有**副本 |
| `pkill -f 'rviz2 -d'` 把自己 shell 杀了 | pkill 的 -f 匹配**完整命令行**，会匹配到执行它的 ssh shell 自己 → 用 `pkill -x 进程名`，或别把模式写进同一条命令 |
| "包不存在"其实是环境没 source | RViz 的 RobotModel 由**显示端**解析 mesh 路径，车端 launch 跑得好不代表 RViz 找得到包 |

**验证启动器是否真的换了配置**（看实际命令行，别信现象）：

```bash
ssh car "pgrep -af rviz2"
```
