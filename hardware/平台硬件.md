## 4. 底置巡线阵列【✅ 已决定采用 —— 2026-09-21 实车实测后】

> ### 🔴 改判记录（2026-09-21，基于实车实测）
>
> **用户实测反馈**：顶部相机做巡线时，"无法看清楚车前面的地面，看得非常前面"
> —— **视野不覆盖脚下**。
>
> **这不是速度问题，是功能问题。** 之前 9/16 的分析（见 4.1）讨论的是"加了会不会更快"，
> 结论是"收益小、先别加"。但实测暴露的是**近处盲区**：靠惯性/记忆过盲区，
> 在 40 cm 通道 + 单侧余量 9.25 cm 的约束下不可接受。
>
> → **改用底置巡线阵列。视觉巡线降级为备份/对照。**
> → 本判断依据实测，**优先级高于 4.1 中基于文档的推断**。

### 4.0 方案要点（按此执行）

| 项 | 决定 | 理由 |
|---|---|---|
| **选型** | **8 路红外**（优先），不用可见光灰度 | 见下方"为什么选红外" |
| 安装位置 | 车头底部前下方，离地 **几 mm ~ 1 cm** | 阵列横跨黑线；太高会串扰 |
| 宽度 | 典型 8~9 cm | ✅ 远小于 21.5 cm 上限 |
| 电气接口 | 阵列 → **小 MCU（RP2040 / Arduino Nano）** → USB 串口 → Orin | **不动原厂 STM32 固件**（见 4.2） |
| 上传数据 | 只传 `line_error` + `junction_flag` | 不必传 8 位原始数据 |
| 采购 | **先问科协有没有**（这类模块很常见） | 没有再买，十几~几十元 |

**为什么选红外而不是灰度（重要）**
- 巡线模块靠**反射光强度**区分黑白：黑线几乎不反射 → 一种电平；白底反射强 → 另一种电平
- **红外版用自身红外光源**，不受可见光干扰 → 赛题**现场光照未知**，这一条很关键
- 可见光灰度版对环境光敏感，现场可能翻车
- 前提：场地地面是浅色（黑引导线本来就必须对比浅底，所以成立）

**装之前必须先确认两件事**
1. **黑色电工胶布的实际宽度** —— 题面没写。它决定：阵列安装高度、阵列宽度、"路口"判定阈值。
   → 群内问科协，或拿到比赛用胶带后实测
2. **底盘控制板有无空闲 IO / I²C / ADC，底部有无安装空间** —— 拍控制板正反面 + 接口丝印

**代价（要认）**
- 加了阵列就**脱离官方 `follow_line`**，需自己写巡线节点 + 重新调 PID
- 8 路给的是**约 1 cm 一档的离散误差**，不如视觉的像素级连续量（对 ±9.25 cm 余量够用）
- 需确认**地面材质**：深色地面会让红外误判（但题目要求黑线对比浅底，应无此问题）

### 4.1 历史分析：底部巡线会不会更快？（2026-09-16，**结论已被实测取代**）

> ⚠️ 本小节讨论的是"速度"问题，结论"收益小、先别加"。
> **但 9/21 实测暴露的是视野问题（近处盲区），性质不同，故最终决定加。**
> 保留本小节作为决策过程记录。

**控制环上确实更快，一个数量级：**

| | 视觉巡线（现状） | 底置灰度阵列 |
|---|---|---|
| 控制环 | 采图 → USB → ROS 话题 → Python 回调 → OpenCV(HSV+inRange) → 求中心 → PID | 直接读电平/ADC |
| 单次延迟 | 数十 ms 量级 | µs ~ ms 量级 |
| 控制频率 | 相机 30~90 fps | 可到 kHz |

**但在本题里这个优势被压得很死：**

1. **迷宫没有长直道可以飙速。** 每格 40 cm，一段直道通常 1~3 格（40~120 cm）。
   加速还没到峰值就得刹车转弯 → "极限线速度"这个变量对总成绩贡献很小。
2. **通道 40 cm / 车宽 21.5 cm，单侧余量 9.25 cm。** 转弯必须减速，
   加减速段占总路程比例很高，巡航速度不是主要矛盾。
3. **真正的瓶颈不在巡线速度**，而在：路口 T/十字判定、死角识别与回退、
   拾取耗时、探索策略走了多少冤枉路。**加灰度阵列对这几条一条都不解决。**

**代价：**
- 官方视觉巡线已跑通且有源码；加阵列 = 自己重写巡线节点 + PID 重调
- 走线/供电/电平隔离，控制板不一定有空闲 IO（可能要挂小 MCU 转串口，见下）
- 要过尺寸关（≤21.5 cm）
- **消耗的是这 54 天里最稀缺的资源：时间**

**当时的结论：现在不要加。** ~~正确顺序是：先跑通官方 follow_line 实测速度 → 若确认是丢线限制速度再加 → 加之前先试裁 ROI~~
> ⚠️ **该结论已被 2026-09-21 实测推翻**（性质不同：实测暴露的是**近处盲区**，不是速度）。
> 当时建议的"裁 ROI"也一并作废 —— 若相机俯角导致画面主拍远处，裁 ROI 救不了脚下盲区。

**一个仍然成立的收益：** 官方 `color_recognize` 与 `follow_line` **共用同一个相机**。
巡线卸给底置阵列后，相机可专心识别方块。

**⚠️ 灰度阵列也有它的坑**：黑胶布实际宽度未知（影响安装高度与阈值）、
灰度版受环境光影响（红外版好一些）、8 路给的是**离散量化误差**（约 1 cm/路），
不如视觉的像素级连续误差。

## 4.2 电气接法（现行方案，不要莽接 Jetson GPIO）

分工：底置阵列管循迹、顶部 RGB-D 管方块识别、双雷达管墙与死路。

**电气接法（不要莽接 Jetson GPIO）**

```
8路灰度阵列
    ↓
小 MCU（Arduino Nano / STM32 / RP2040）
    ↓ USB 串口
Jetson Orin NX（ROS2 节点）
```
上位机只需收到 `line_error` + `junction_flag`，例如：
```
-1.7,0
 0.1,0
 0.0,1   ← 到路口
```
**理由：完全不动原厂底层控制固件**，避免为加传感器把电机控制/micro-ROS 搞炸。

**尺寸合规**：典型 8 路板约 8~9 cm 宽，远小于 21.5 cm 上限。✔

**采购前先问科协**：这种模块太常见，科协很可能一抽屉都有。
> "科协有没有 8 路灰度/红外巡线模块？我想装在 M3 Pro 底盘前下方做黑胶带高速循迹。"

## 5. 路口识别：T 与十字的区分【技术结论】

**单排横向阵列在"刚压到路口"的瞬间分不出 T 和十字** —— 两种情况都可能是 `11111111`。

解法：利用时间序列，**过路口后再往前探 3~5 cm**，看中间探头：

| 越过后中间探头 | 判定 |
|---|---|
| 仍有黑线（如 `00011000`） | **十字**（前方纵线继续） |
| 全白（`00000000`） | **T 型**（前方无路，只有左右） |

- 用**编码器增量**控制"再前进几厘米"，比按时间估稳得多
- 更狠的做法：装**前后两排**阵列，不用停车探
- 对本题（每格 40 cm、路口几何规整）**单排 + 前探足够**

## 6. 里程计的边界【技术结论】

- 有码盘，但**麦轮横移、转弯、打滑会让纯轮式里程计累积误差**
- 适合做**短距离动作控制**（"再前进 4 cm"、"转约 90°"）
- **不适合**只靠码盘跑完整个 7×7

三者结合：**灰度纠横向、码盘管短距/转角、雷达管墙面与距离兜底。**
